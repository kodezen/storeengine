### 6. Core — Decimal Quantity / Unit of Measure ✅ complete (one low-priority item left)
All four bugs from the report, fixed and verified live via a real by-weight test product ($25/kg) through the actual storefront + checkout:
- `checkout-service.php:836` — `absint($values->quantity)` → `Quantity::parse(...)`. Verified: a 2.5 kg checkout via COD produced an order with `_quantity = 2.5` in the DB (not 2), both via a direct method-level test and a full real browser checkout.
- **Self-discovered bug's fix now applied**: `formatting.php` had the *same* `absint()` truncation in **three** places, not just the one previously flagged — `get_price_excluding_tax()` (originally reported), plus `get_price_including_tax()` and `get_price_to_display()` (found by grep while fixing the first). All three now use `Quantity::parse()`. Verified via wp-cli: all three return `62.5` for `qty=2.5 @ $25`, not `50`.
- Storefront product-page quantity `<input>` hardcoded `step="1" min="1"` — root cause was `storeengine_get_quantity_args()` in `includes/frontend/functions.php` hardcoding `step`/`min_qty` to `1` for ANY product (the fractional-aware `Quantity` class was never wired in at all — literal commented-out placeholders were sitting in the code: `// $product->get_purchase_quantity_step();`). Fixed to derive from `Quantity::step()`/`is_fractional()`. Verified: `step`/`min` now read `0.001` for the weight-mode test product, `checkValidity()` returns `true` for `2.5`.
- Cart-page quantity stepper — this was actually **two** separate bugs, both fixed:
  1. `templates/global/quantity-input.php` unconditionally ran the displayed `value` through `absint()`, truncating `2.5` → `2` on display. Fixed to pass numeric values through untouched.
  2. `templates/cart/cart-list-table.php` called `storeengine_quantity_input()` with no product/price context at all, so step/min defaulted to whole units on the cart page even after the fix above — meaning clicking "+" still round-tripped through a `step=1` calculation. Fixed by passing the row's `Price` object through. **Also** fixed a second bug in the JS click handler (`dev_storeengine/utils/ssr.js`'s `QtyInputHandler`): `parseInt(val) + incMnt` truncated the *current* value before adding the step, so even with the correct step now available, clicking once still collapsed `2.5` to `2.001` instead of `2.501`. Fixed to use the already-correctly-parsed float. Verified live: cart shows `2.5`, clicking `+` produces `2.501`, not `3`.
- Added: unit-of-measure label ("$25.00 /kg" / "$30.00 /kg") on the product page (`templates/single-product/price.php`), cart line items (`templates/cart/cart-list-table.php`), order-confirmation line items (`templates/shortcode/order-details.php`, "Qty: 1.75 kg"), **and the shop/archive listing grid** (`templates/loop/price.php` + `templates/loop/prices.php` for the multi-price-tier variant) — the last one was missed in the first pass and only caught by a dedicated regression sweep afterward; it's arguably the most visible instance since it's the first price a shopper sees. ## Established workflow / conventions (read before continuing)

**Editing:**
- PHP: `php -l <file>` after every edit.
- JS: syntax-check via babel directly (NOT eslint/wp-scripts): `node -e "const babel = require('./node_modules/@babel/core'); babel.transformFileSync('path/to/file.js', { presets: ['./node_modules/@babel/preset-react'], babelrc: false, configFile: false });"` from the `storeengine-pro` (or `storeengine`) directory.
- **NEVER run `wp-scripts lint-js --fix` or any repo-wide linter.**

**Rebuilding:** `bun run build` in the relevant plugin dir (`storeengine` for core/frontend changes incl. `dev_storeengine/utils/ssr.js`, `storeengine-pro` for pro admin JS). Both plugins now have `bun.lock` committed to the working tree (uncommitted, see below) — `bun install` is fast and was used throughout this session in place of `npm`/`wp-scripts`' own installer. Always `git status --porcelain | grep -v "^ M assets/build"` afterward to confirm only the intended source files + build output changed.

**Verification, in this order:**
1. `wp eval '...'` for backend logic — but note: **cart/session state does NOT persist between separate `wp eval` invocations** (each is its own process; the cart is tied to the browser's cookie-based session). To test cart/checkout logic end-to-end from wp-cli, do it all in ONE `wp eval` call (`wp_set_current_user()`, add to cart, run the checkout method, assert, all in the same script). To reset the state a live browser page is showing, do it via a `fetch()` call **from inside the Playwright page context** (`credentials: 'same-origin'`), not via a separate wp-cli command — they're different sessions.
2. Live Playwright browser pass — pattern (copy exactly):
   ```js
   const { chromium } = require('/home/abdullah/Work/office/kodezen/wp-content/plugins/storeengine/node_modules/playwright');
   const context = await chromium.launchPersistentContext(OUT_DIR + '/chrome-profile', {
     headless: false, ignoreHTTPSErrors: true, viewport: { width: 1400, height: 1000 },
   });
   const page = context.pages()[0] || (await context.newPage());
   page.on('dialog', async (d) => { await d.accept(); }); // auto-accept confirm() dialogs; override with a value for prompt()
   ```
   Prefer `waitUntil: 'domcontentloaded'` over `'networkidle'` for admin pages — `'networkidle'` intermittently hangs 30s+ on this app (some background polling never goes idle). Wrap navigation in a 3-4x retry loop.
   **Auth**: no known password for the `abdullah` admin user. Generate real auth cookies instead of guessing a password:

   then `context.addCookies([...])` with those two (logged_in on path `/`, secure_auth/`wordpress_sec_*` on path `/wp-admin`).

**Known gotchas (this session):**
- **Addons ship inactive by default.** `suppliers`, `inventory-pro`, and `returns` were all activated this session via `wp eval '\StoreEngine\Addons::activate("slug");'` (NOT an option you can just `update_option` — there's a real API, `\StoreEngine\Addons::activate()`/`deactivate()`, option name `storeengine_addons`, JSON-encoded object). Left active; matches the report's own precedent.

Click the combobox input directly (may need `{ force: true }` if an invisible overlay input intercepts), then click the option text.

A stray leading-slash typo in the `storeengine_permalinks` option's `product_base` (stored as `/product` instead of `product`) was also found and corrected — that part was a genuine data bug, now fixed via `wp option update`, unrelated to the WooCommerce collision.
